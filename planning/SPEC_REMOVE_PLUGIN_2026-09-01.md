## Library reuse (mandatory)

`remove-plugin.praat` sets the library flag and includes the
installer to reuse its procedures — never re-implements them:

    emlManager_harnessMode = 1
    include ../plugin_EMLPraatPluginManager/install-from-disk.praat

CORRECTED (re-measured 1 Sep): Praat resolves EVERY include —
nested ones included — relative to the OUTERMOST running script's
folder, not the file containing the include line. The earlier
"relative to the including script" claim was wrong. The ../<folder>/
form above is therefore the pinned form: it works when the harness
(outermost in harness/) includes the module, and when the module
runs from the menu (outermost in the plugin folder, where ../<folder>/
folds back to itself). Because it names the plugin folder, a folder
rename would silently break it: `tools/build_installer.py --check`
asserts the include line names the actual plugin_* folder, so a
rename fails loudly until the line is updated.

Reused: text wrapping (one comment field per wrapped line — pause
windows do not wrap), sanitized boolean labels, pagination at 12,
the recursive tree walk, the folder placement procedure
`emlManagerPlaceFolder` (system `cp -R` / `xcopy` — the mechanism
whose results the E2E record measured byte-identical; it uses
`runSystem_nocheck` and reports through `.ok` — see Execution
step 1), and the archive folder name
constant (`emlManager_archiveName$`). Both files sit in the plugin
folder; the include form and its resolution rule are pinned above. System commands are permitted here exactly where the
installer already uses them; the no-system-commands constraint
binds the standalone install file only.

MEASURED LIMITS (2026-09-01, 6.6.30): `filesAreIdentical` does not
exist; `readFile$`/`writeFile` is not byte-safe for binary or
non-ASCII content (null bytes dropped, UTF-16 switching). True
in-Praat byte comparison is therefore impossible at this floor;
verification is structural (below). Revisit if the floor ever
rises to a version providing a native file comparator.

## Dialog 1 — selection

Title "Remove a plugin". Lists every `plugin_*` folder in
`preferencesDirectory$` as an UNCHECKED boolean, sanitized labels per
the existing rules, paginated at 12. The manager's own folder gets
the label suffix " (this is the Plugin Manager itself)". Buttons:
"Quit" / "Continue", default Continue. Quit exits with the existing
cancelled message. Zero boxes checked + Continue → the existing
none-selected exit path.

## Dialog 2 — the gate (Ian's ruling, verbatim intent)

Pressing Continue NEVER removes anything. A second dialog, title
"Confirm removal", states exactly what will happen, then requires an
explicit switch:

- Per selected plugin, wrapped lines: its folder name; its file
  count and folder count (measured by the tree walk); the exact
  archive destination `<prefs>/<archive>/<folder>__<version>` where
  `<version>` is the plugin's VERSION first line, or `no-version`
  when absent; if that destination exists already, `__2`, `__3`, ...
  is appended until free.
- Then, always: "The plugin is first copied to the archive with the
  same mechanism installs use."; "The copy's complete file inventory
  is verified against the original before anything is deleted.";
  "Settings a plugin keeps outside its own folder are not touched."
- If the manager itself is selected, additionally: "You are removing
  the Plugin Manager itself."; "Its menu commands disappear after
  the next restart."; "The archive keeps a complete copy."; "To
  reinstall, run the install file from the repository or from
  wherever you downloaded it."
- ONE boolean, label "Archive and remove the plugins listed above",
  DEFAULT 0.
- Buttons: "Quit" / "Archive and remove", DEFAULT BUTTON Quit.

Button logic: Quit → cancelled exit, nothing touched. "Archive and
remove" with the boolean still 0 → a notice dialog (OK button):
"Nothing was removed. To proceed, switch on 'Archive and remove the
plugins listed above' and press the button again." — then Dialog 2 is
shown again. This loop has no retry limit; Quit always exits.

## Execution (per plugin, only after the gate passes)

1. Copy the plugin folder to the archive destination with
   `emlManagerPlaceFolder`. AMENDED (measured): that procedure uses
   `runSystem_nocheck` and reports through its `.ok` result — it
   does not raise. The module checks `.ok`; `.ok` = 0 → stop,
   nothing deleted, report the copy failure.
2. Structural verify: build the recursive relative-path inventory
   (every subfolder and file path, sorted) of the original and of
   the archive copy. ANY difference — missing path, extra path,
   different counts → stop before deleting anything, report the
   first differing path, and state that nothing was removed and the
   partial archive copy may be deleted by hand.
3. Delete the original files (`deleteFile`), then the emptied folders
   bottom-up (`deleteFile` on an empty folder removes it — measured
   at 6.6.30 on Linux). A folder that refuses deletion is NOT an
   error: record it and continue (Windows may refuse; the plugin no
   longer loads once setup.praat is gone).

HIDDEN FILES (measured): Praat's `fileNames$#`/`folderNames$#`
cannot enumerate dot-files, so the inventory and the delete walk
cover only visible entries, while the `cp -R` archive copy includes
hidden files. Consequences, pinned: a folder left non-empty by a
hidden file takes the recorded-not-fatal branch; the completion
dialog's remained-folders line reads "<k> folders remained (they
may contain hidden files Praat cannot see; the archive copy
includes them)."; Dialog 2's inventory sentence says "complete
file inventory" of what Praat can enumerate — do not claim more.

GATE READBACK (measured, from the failed drive): Praat lowercases
the FIRST character when deriving a pause-form variable name from
a field label. Any label-to-variable derivation must lowercase the
first character; the shared helper is the canon — fix it there
once, and check no existing caller depended on the unlowered form
(all current callers start with lowercase "plugin_").

## Completion dialog

Title "Removal complete", OK button. Per plugin: "archived to
<destination>", "<n> files archived, originals removed", and — only
when folders remained — "<k> folders remained (they may contain
hidden files Praat cannot see; the archive copy includes them)."
Final line: "Restart Praat. The removed commands disappear from the
menus." If the manager removed itself, instead: "Restart Praat. The
Plugin Manager's commands will be gone."

## Harness (headless, run with the barren build)

`harness/run_remove_plugin.praat` builds throwaway plugin fixtures
under a temp folder and drives the work procedures directly (the
dialogs are skipped via the library flag; the procedures take the
selection as inputs). Named checks, at minimum: archive path
construction incl. no-version and collision suffix; copy+verify green
path removes everything including folders; RED: a deliberately failing copy (unwritable destination) yields
`.ok` = 0 and nothing is deleted; RED: seeded inventory mismatch (harness deletes one archived
file between copy and verify via a hook flag) → verify fails, NO
original deleted;
RED: gate boolean 0 → work procedures never called (checked at
dialog-flow level in the GUI drive, and by asserting the work
procedure requires an explicit argument the dialog only passes on
success); folder-delete-refusal fallback: a REAL assertion — seed a hidden
file (write ".hidden" by explicit path; Praat can write what it
cannot enumerate) inside a fixture plugin, run the full removal,
assert the dot-file's folder remains, remainedCount ≥ 1, and every
visible file is gone. No unconditional PASS lines anywhere in the
harness — every counted pass asserts something.

## Praat facts the implementation relies on (all measured)

`deleteFile` removes a file, and removes an EMPTY folder;
`folderNames$#`/`fileNames$#` enumerate; `createFolder` is not
mkdir-p (create parents one level at a time); include resolves
relative to the OUTERMOST running script's folder, nested includes
too (see the corrected paragraph in Library reuse); the library
flag suppresses the installer's main sequence.
