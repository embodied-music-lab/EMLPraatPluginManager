# Pinned specification — Create install file (v0.7.0)

Every design decision below is made. Where this text is ambiguous or
impossible as written, STOP and report the question — do not
improvise.

## What it is

A new manager command generates a small standalone install script
INSIDE a plugin's folder. The author zips the folder as usual; a user
unzips it anywhere, opens the install script in Praat, runs it, and
the plugin installs — no manager required on the user's machine. The
script catalogs file NAMES, never file contents: at install time it
copies its own parent folder's contents into the preferences folder.

## Files

- NEW `plugin_EMLPraatPluginManager/create-install-file.praat` — the
  module (library-includes install-from-disk.praat with the harness
  flag, same pattern as remove-plugin.praat).
- `plugin_EMLPraatPluginManager/setup.praat` — ONE added line
  registering "EML Plugin Manager: Create install file for a
  plugin..." after the Remove command, same syntax.
- NEW `harness/run_wrapper_installer.praat` + fixtures.
- Maintainer regeneration of the root install file
  (tools/build_installer.py) after plugin edits.
- Nothing else.

## The generator command

Dialog 1: single-select (optionMenu) of the installed plugins
(`plugin_*` folders passing the installed canon; ghosts excluded),
bare capped labels per the existing label canon.

Dialog 2: one text field "Version", prefilled with the first line of
the plugin's VERSION file when present, else "1.0.0", with the
comment line: "Numbers and periods only (for example 1.2.0)."
Validation: the value must match digits and periods with at least
one digit; anything else → a notice repeating the instruction, then
the dialog again (Quit always exits). On acceptance the plugin's
VERSION file is written (one line, the value) — creating it when
absent, overwriting when present.

Generation writes `install-<name>.praat` into the plugin folder,
where `<name>` is the folder name without the `plugin_` prefix. The
wrapper is pure ASCII and contains, baked at generation time
(ASCII GUARD, amended: any non-ASCII character in a baked report
line is replaced with "?" at generation; a plugin FOLDER NAME
containing non-ASCII refuses generation with a notice naming the
folder — names are load-bearing in paths, report text is not):

- the plugin's TRUE folder name (never read from the runtime
  parent — the unzipped parent may carry a mangled name like
  `Praat-plugin_X-main`);
- the version string just written;
- the manifest: the sorted recursive relative paths of every file in
  the folder (the wrapper itself included — it travels);
- the command report: the parser's English lines for the plugin's
  setup.praat, generated by the existing report canon;
- embedded copies of exactly three canons, emitted mechanically from
  the manager's own procedures: the installed test (setup.praat
  present), the component-wise version comparator, and the word-wrap
  canon (the wrapper's dialogs wrap at the canon width). The
  label-capping subsystem is excluded — the wrapper has no
  checklists.

Regenerate-on-change rule, stated in the wrapper's header comment
and the docs: adding or removing files, or changing setup.praat's
commands, calls for re-running Create install file; editing a file's
contents does not.

## The wrapper at runtime

Praat floor check first (6.6.30, same constants pattern as the root
install file). Then, in order:

1. Locate itself: relative paths resolve against the outermost
   running script's folder (measured), which is the plugin folder as
   unzipped, whatever it is named. Verify the manifest: every listed
   relative path exists beside it; any missing → a notice naming the
   first missing path and "re-download the plugin", then exit.
   Nothing is written before this passes.
2. Conflict check on the BAKED name `plugin_X` in the preferences
   folder:
   - absent → proceed;
   - ghost (folder without setup.praat) → proceed; completion notice
     adds the reused-leftover line;
   - installed → read its VERSION first line (absent = unknown) and
     compare with the embedded comparator. One dialog, title
     "Already installed", states: the installed version, this
     installer's version, and one status line ("This installer is
     newer." / "Same version." / "The installed copy is newer." /
     "Versions cannot be compared."). Then the offers:
     - Button "Keep a backup and install" (DEFAULT for the
       newer-incoming case; plain button — the action is
       recoverable): renames the installed folder to
       `old_plugin_X`, appending `_2`, `_3`, ... if that name
       exists. The dialog states: "The current copy is renamed to
       old_plugin_X. Praat ignores folders that do not start with
       plugin_; delete it by hand when you no longer want it."
     - Boolean "Delete the installed copy instead", DEFAULT 0, with
       the line "The installed copy is deleted, not archived. The
       EML Plugin Manager archives before replacing." Clicking the
       install button with this boolean ON deletes instead of
       renaming; the boolean is the gate — with it OFF the rename
       path runs.
     - Button "Quit" — DEFAULT BUTTON when the incoming version is
       same, older, or not comparable. Nothing touched.
3. Resolution before placement, strictly: the rename (or delete)
   completes before any copying; a failure there → notice and exit
   with nothing else touched.
4. Placement: create `prefs/plugin_X`, then the system copy of the
   parent folder's CONTENTS into it (the platform-branched mechanism
   the manager's own placement uses; contents-copy so the mangled
   parent name never matters; dot-files ride along).
5. Structural verify: every manifest path exists under the
   destination; any missing → notice naming the first missing path,
   stating the copy is incomplete and may be deleted by hand,
   nothing else done.
6. Completion notice (pause dialog, OK, canon wrap width): installed
   name and version, the baked command report lines, the
   reused-leftover line when 2 hit the ghost case, and "Restart
   Praat." Every terminal message is a notice dialog + silent exit
   (never exitScript with text — measured boilerplate).

VERSION-CORRECT LOCATION, pinned (measured 1 Sep: Praat 6.6.30
reports ~/.praat-dir and Praat 7.0.02 reports ~/.config/praat on
Linux — the variable tracks the running version): the wrapper reads
`preferencesDirectory$` AT RUNTIME, never bakes a preferences path
at generation. A wrapper generated under Praat 6 must install into
Praat 7's folder when run under Praat 7, and vice versa. No
hardcoded preferences path may appear anywhere in generated text.

SAFETY, pinned: every system-command path (copy, rename, delete) is
constructed ONLY from `preferencesDirectory$`, the baked literal
folder name, and the wrapper's own resolved parent — never from any
user-typed text. The delete uses the platform-branched remove the
same way placement branches copy. Windows behavior is untested at
this floor: a failed rename or delete is a clean stop (step 3), so
the risk is a refusal, never a broken install.

## Harness (headless, real assertions)

Generator: version-field validation (rejects letters, spaces, empty;
accepts 1.2.0); VERSION file written/overwritten; wrapper generated
with correct baked name, version, manifest count, report lines;
wrapper is pure ASCII; embedded canon procedures byte-match the
generator's emission for a fixture plugin. Wrapper runtime (drive
the work procedures under a harness flag): manifest-verify red
(delete one file → named refusal, nothing written); fresh install
green (structural verify passes; contents byte-identical via the
harness's own diff); ghost → proceeds with the leftover line;
conflict matrix — newer/same/older/unknown each produce the pinned
status line; rename path creates old_plugin_X (and _2 on the second
run) and installs; delete path only with the boolean gate on;
path-construction audit: assert the generated wrapper contains no
system-command line interpolating anything but the pinned
components.

## Drive (GUI, evidence)

Generate an install file for a real plugin (tgutils) in the sandbox
via the new menu command (screenshot the version dialog), zip the
folder, unzip it under a MANGLED outer name in /tmp, run the wrapper
from there: fresh install lands under the true name (diff -r
byte-identical). Re-run the wrapper: the Already-installed dialog
(screenshot), take the rename path, verify old_plugin_tgutils
exists and the new copy installed. Re-run once more with the delete
boolean ON: installed copy deleted, no old_ folder added. Completion
notice screenshot showing the baked command report. VERSION 0.7.0 at
the end of the round; README gains the feature line.
